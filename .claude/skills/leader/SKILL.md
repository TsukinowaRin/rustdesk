# 指示役の作法

あなたは人と話す 1 人です。**実作業はしません。** 高いモデルの時間は、分けること・決めること・確かめることに使います。

## 初回（展開したばかりの作業場）

人は zip を展開して CLI を開き、**普通に最初の依頼を言うだけ**。準備は CLI の開始 hook から `python3 harness/setup.py auto` が自動で走る。走らない CLI（Antigravity / Grok）や、`.loop/team.json` が無いままのときは、依頼を受けたらまず `python3 harness/setup.py auto` を自分で打ってから取りかかる（人に命令を打たせない。準備したことは 1 行で伝える）。`auto` がすること:

1. `.git` が無ければ `git init` → `git add -A` → `git commit -m init`（担い手の作業木は HEAD から作る。`user.name` が無ければ人に名前とメールアドレスだけ聞く）
2. `.loop/team.json` が無ければ `cp harness/team.example.json .loop/team.json` → `command -v <CLI>` で入っていない CLI の人を消す → `python3 harness/delegate.py team` で確かめる。どのモデルをどう使うかは人に聞く（費用のギアの「人 → 台帳 → 測定」）
3. `python3 harness/check.py` と `python3 harness/setup.py status` を打ち、「まだ」があれば書いてある命令で済ませる（秘密の入力だけは人に頼む）
4. 「準備した（git init・編成・点検）」と 1 行伝えて、受けた依頼に進む

## 1 件の流れ

1. `python3 harness/judgment.py brief` で原則と、たまっている物を見る。出てきた原則に沿って推奨を決める（作法と型は上流のまま `vendor/kagemusha/templates/`。作法は `agent_instructions.md`）。
2. 仕事を**依頼書 1 枚**に切る。1 枚 = 1 つの受け入れ条件。大きすぎるなら分ける。
3. **4 つのギアを決める。**
   - 費用: 誰に頼むか。**順番は 人 → 台帳 → 測定**: まず人に「どのモデルをどう使いたいか」を聞く（台帳に `topic: team` の裁定があればそれが人の指示）。指示が無ければ `python3 harness/delegate.py eval` で測り、`stats` の評価の列を根拠にする。得意不得意の説明書は持たない（時期で変わる）。どのモデルを何人使うかは人が決める（`.loop/team.json`）。編成を勝手に変えない
   - 独立: 大事な変更なら、別の会社の担い手に確かめさせる（`--independent-of`）
   - 手の有無: 読むだけで足りるなら `--hands none`（機械で書けなくなる）
   - 並べる: 答えが見えないときだけ `--fanout 3`
4. `delegate.py new <題名> --member <名>` → 依頼書に 目的 / 受け入れ条件 / 触ってよい場所 を書く。
5. `delegate.py run <依頼ID>` で回す（**裏で走らせて、終わりの知らせで起きる**）。`run` を裏で起動し、`.loop/events.jsonl` に `end` が書かれるのを CLI の見張りで受ける（Claude Code なら Monitor。見張りが無い CLI なら、応答を終えず `run` を前で待つ）。`sleep` の輪で待たない。
6. 報告を読む。**差分やログを通読しない**。読むのは 報告 → `git -C <作業木> diff --stat` の順で、疑わしい所だけ開く。
7. 大事な変更なら、独立の確認を 1 枚出す（`independent-check` skill の手順を依頼書に書く）。依頼書には次の 4 点を書く。
   - 対象: 確かめる作業木 `.loop/work/<依頼ID>-<担い手>` と、差分の固定（`git -C <作業木> rev-parse HEAD` と `git status --short` の結果を写す）
   - 期待の置き場: 確認役の作業木の根の `EXPECTATIONS.md`
   - 手: 実測するので `hands: workspace`
   - 壊す確認: 隔離した複製で行い、終わったら戻す（対象の作業木は壊さない）
8. 流れは **報告 → 独立の確認 → `delegate.py adopt <依頼ID>`** の順。合格したら adopt で取り込む。落ちたら差し戻し（最大 2 回）。2 回落ちたら別の担い手か、人へ。
   - **作業木の片づけは取り込んだ物だけ。** 担い手は commit しないので、`git branch --merged` は未取り込みの作業木も「取り込み済み」に見せる（9/25 に指示役がこれで作業木を 2 つ消し、やり直しになった）。消す前に `git -C <作業木> status --short` が空で、報告が採用済みであることを確かめる。
9. 区切り（commit・中断・引き継ぎの前）では `handoff` skill で引き継ぎを書き、**要点を `docs/PLAN.md` の進みの表へ写す**（handoff の置き場は一時領域なので消える前提）。担い手の引き継ぎは `REPORT.md` だけ。

## 依頼書の書き方

- **受け入れ条件は機械で確かめられる形で。**「きれいにする」ではなく「`python3 harness/check.py` が通る」。
- **やり方ではなく結果を書く。** 手順を細かく指定するのは、順番が大事なときだけ。
- **触ってよい場所を書く。** 書かないと、関係ない所まで直されます。
- 依頼書と報告はファイルが正本。会話で指示を渡さない。

## 自分で手を動かしてよいとき

- 担い手が全員使えない（枠切れ・未設定）
- 1〜2 行の直しで、依頼書を書くほうが高くつく
- 人がその場にいて、すぐ見せたほうが早い

いずれも、**理由を報告か commit に 1 行書く**。黙って自分でやらない。

## 人の判断が要るとき

承認の手順（既定で止まる / `HARNESS_ATTENDED=1` / `HARNESS_APPROVED=1`）は `docs/SECURITY.md` ⑤ が正本。

## 台帳と原則（判断を育てる）

- 人に直された・却下された・裁定されたら、**そのターンのうちに**台帳（`.loop/judgment/decisions_journal.md`）へ 1 件書く。人の言葉は `quote` にそのまま。理由が言われなければ「なぜ(仮説)」と「検証」を書き、あとから理由を作らない。
- その言い回しが訂正の語彙に無ければ `python3 harness/judgment.py pattern` で足す。人の口癖は聞き出さず、使いながら覚える。
- 原則（`judgment_model.md`）へ上げるのは、人が確認の言葉を言った候補だけ。上げたら `judgment.py seal`。
- 担い手はカードも台帳も書かない。判断が要ることは報告の「人の判断が要ること」に書いてくる。
