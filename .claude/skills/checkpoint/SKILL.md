# Checkpoint

## 使う場面

- commit 前、中断前、handoff 前、レビュー依頼前の区切り。

## 手順

1. 変更ファイルを特定し、変更範囲に最小で有効な検証（test / build / type-check / lint / smoke）を実行する。実行できなかった検証は、理由と未確認範囲を隠さず明記する。
2. diff を見て、意図しない変更、危険なコマンド、docs 更新漏れがないか確認する。
3. ユーザーから見える挙動、コマンド、運用ルールが変わったなら、関連する docs だけを同時に更新する。不要になった doc は削除するか、見つけやすい場所で obsolete と明記する。
4. `docs/WORKLOG.md` に停止点を残す: 目的、変更、実行したコマンドと結果、判断と仮定、未完了、ブロッカー、次の一手（次に最初に読む文書と、最初に実行するコマンド）。失敗した試行も価値があれば残す。エントリは再開に必要な範囲で簡潔にし、読むときは先頭の直近エントリだけ読む。
5. 複雑作業なら `docs/EXECPLAN_*.md` の進捗・停止点・発見事項を更新する。要求や受け入れ条件がズレたなら `docs/REQS.md` へ反映する。完了した依頼を REQS へ蓄積せず、WORKLOG のエントリが直近3エントリを超えたら、古い分を `docs/legacy/*_ARCHIVE_*.md` へ退避する。アーカイブは通常タスクで読まない。
6. 上位計画（ExecPlan の original 領域、または plan / impl pair）がある作業では、計画の受け入れ条件・予定変更範囲と最終 diff を突き合わせ、承認済み deviation と実変更が対応していること、未記録の範囲外変更が無いことを確認する。runner は「記録されなかった逸脱」を検出できないため、この突き合わせが最後の砦になる。
7. 最後に、何を変えたか / 何を検証したか / 何が残リスクかを、commit message や PR 説明へ転記できる形で要約する。検証していないことを成功したように書かない。

## 完了条件

- chat 履歴なしで、別エージェントが docs だけから再開できる状態になっている。
