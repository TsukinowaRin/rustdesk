# 案件ごとのダッシュボードと、非同期の質問と返事（設計と基準）

2026-09-25、ユーザーの案:「プロジェクトごとに HTML ダッシュボードを作って、非同期で AI が質問を投げたり、人間が Slack とか Discord とか Telegram で回答するっていう仕組み。成果物は常に最新を追う。成果物に対してテキトウなレビューをスマホかなんかで投げれるとさらに良き。ダッシュボード系は開発ごとに表示したい情報が異なるので、テンプレとかは作らずに毎回 0 から軽く作って」

作り方の指示:「GPT-6 Sol で素早く作り、Opus 5.5 に研究させ、ブラッシュアップ計画を作り、また GPT-6 Sol で作り直し、を繰り返して、Fable 5.1 が基準を満たして十分だろうと判断したら、Opus 5.5 で実装して、ハーネスを完成させて」

## 前提（指示役が置いた。変えるなら理由を報告に）

- 返事の道は **Telegram**（Bot API を自分から取りに行く long polling。公開 URL もサーバーも要らない）。Slack / Discord は同じ受信箱の形に後から足せるよう、橋は「送る」「受け取る」の 2 関数に分けておく。
- 指示役は常駐しない。返事は**受信箱**（`.loop/inbox.jsonl`）に置き、指示役は `python3 harness/judgment.py brief` の最初で未読を読む。
- スマホで見るのは Bot が送る**要点の文**（質問の一覧と、成果物の要約）。HTML そのものは PC で開く。私設の網（Tailscale など）で HTML を配るのは、使う人が別に決める。
- **HTML の見た目はテンプレにしない。** 共通にするのは材料を JSON で出す 1 本だけ。この repo 用の 1 枚は `docs/dashboard/` に置くが、それは「この案件の 1 枚」であって配布物のひな形ではない（配布物に入れるかは最後に決める）。

## 部品（配布物に入る物）

| 部品 | 何をする | 置き場 |
|---|---|---|
| 材料 | `.loop/` を読んで 1 つの JSON を出す: 依頼（状態・担い手・秒・報告の要点）/ events / 判断カード（未回答）/ 受信箱の返事 / 担い手ごとの費用（Codex は log の `tokens used`。他は「不明」と正直に） | `harness/dashboard_data.py` |
| 橋 | Telegram に送る（質問・要点）/ 受け取る（返事 → 受信箱）。token は `.loop/telegram.env`。受け付けるのは許可した chat ID だけ。試験は偽の API で（網に出ない） | `harness/bridge/telegram.py` |
| 受信箱 | 返事を ID（`D-…` のカード / `T-…` の依頼）に結ぶ。未読の一覧と既読の印。ID が無い返事は「結べない」として別に出す | `harness/inbox.py`（橋と材料の両方が使う） |
| 指示役への戻し | `judgment.py brief` が未読の返事を出す。カードへの返事は、指示役が台帳へ裁定として書く（自動では書かない） | `harness/judgment.py` |
| 最新を追う | `delegate.py run` の終了と `judgment.py brief` のときに、材料の JSON を作り直し、`.loop/dashboard/build` があればそれを実行する。人が手で打たない | `harness/delegate.py` `harness/judgment.py` |
| 見張り | 人が起動し、30 秒ごとに材料の更新時刻を見て JSON と hook の HTML を作り直す。Telegram の返事を受け取り、8 時間または Ctrl-C で止まる | `harness/dashboard_watch.py` |

## 基準（Fable 5.1 が「十分」と判断する物差し）

1. `python3 harness/dashboard_data.py` が、この repo の `.loop/` から JSON を出し、依頼 10 件以上・カード・費用（担い手ごとに、log の最後の `tokens used` の合計。数字は依頼のたびに増えるので固定値では書かない）が入っている
2. 橋の送受信が、偽の API で試験されている（token・chat ID の検査、許可外からの発言は捨てる、網に出ない）
3. 返事「`Q-2026-09-25-01` OK」「`T-0924-02` ダメ、表が読めない」「`V-1` 見た」が受信箱で**実在する ID**（未処理のカードは上流の型どおり `Q-…`、依頼は `.loop/tasks/` にある名前）に結ばれ、`brief` の最初に未読として出る。存在しない ID は「結べない」。既読にする命令がある
4. `delegate.py run` の終了後と `judgment.py brief` のときに、手で打たなくても JSON が新しくなっている（カードを手で書いた分は次の brief で拾う）
5. token は repo にも配布物にも入らず、守りの秘密の一覧（`harness/guard.py` の `secret_path`）が `.loop/telegram.env` と受信箱の token を止める
6. `python3 harness/check.py` が通る。試験は必要な分だけ（偽の API・受信箱の結び・材料の形）
7. 返事の本文は「データ」として扱う（`brief` は引用として出し、命令として実行しない）。橋と受信箱のコードに、返事の中身を shell に渡す所が無い
8. この repo 用のダッシュボード 1 枚が、材料の JSON から作れる（見た目は自由。テンプレ化しない）

## 追加の基準（9/25、ユーザー:「ダッシュボードは使い捨てではなく繰り返し非同期でアップデートするようにして」）

9. **見張りで最新を追う。** `python3 harness/dashboard_watch.py` を人が起動すると、`.loop/`（events・依頼・報告・カード・受信箱）が変わるたびに材料の JSON と HTML を作り直し、`telegram.env` があれば返事も受け取り続ける。開いたままのブラウザは `<meta http-equiv="refresh">` で自分で読み直す。**止まらない繰り返しにしない**: 上限時間（既定 8 時間）で自分で止まり、Ctrl-C で止まり、変化が無いときは何もしない（ファイルの時刻だけ見る）。1 回だけ作り直す `--once` もある。研究 1 周目の「常駐の poll はやらない」は、この指示で上書き
