# ハーネス全体の改善の輪（2026-09-25〜）

ユーザーの指示（9/25）:「このループの対象は、HTML だけでなく、ハーネス全体である。このコンピュータで利用可能な CLI で一通りテストをして、改善計画を作り、改善を繰り返して。」
作り方は `docs/design/DASHBOARD.md` と同じ: **GPT-6 Sol が作る → Opus 5.5 が研究して計画 → GPT-6 Sol が直す → Fable 5.1 が基準で判定**。足りなければ研究へ戻る。

## 本来の目標（9/25、ユーザーの言葉で直した）

「費用が見えるではなく、効率の良い運用をして、結果として費用を節約できるあるいは効率的にできる、というのが本来の目標。適当なモデルでもできることに Fable 5 を使ったりしないとか、モデルの得意分野を把握して、適切に仕事を割り振るとかが目的。MoA というのはそういうもの。そして、どのモデルが何が得意か、とかはその時によって変わるので、モデルの性質の説明書をハードコードしてはならない。その時の環境に応じてユーザーが指示あるいは自動で調べて情報を取得するべきである。」

- 費用の記録（`stats` のトークン）は**手段**。目標は、賢いモデルを要る所だけに使い、安いモデルで足りる仕事は安いモデルに回すこと
- **順番は 人 → 台帳 → 測定**（9/25 ユーザー:「勝手にモデルを測るんじゃなくて、まずユーザーに聞いて指示をもらい、それがない場合は自分でベンチマークしてチェックする」）。人の指示は台帳に `topic: team` で書き、台帳は作業場をまたいで共有する（`docs/design/JUDGMENT-STORE.md`）
- **得意不得意の説明書は持たない**（`team.json` の notes は人の覚え書き。配布物のひな形に例文を入れない）。指示が無ければ **測る**: `harness/evals/` の小さな課題を各担い手に流し、成功率・秒・トークンを `stats` に出す。指示役は依頼書の `member:` を選ぶとき、その数字と人の指示を根拠にする
- 測った結果は `.loop/` に置く（時期で変わる物は配らない）

## 触ってよい物・だめな物（ユーザーの決まり、9/25）

「ハーネスの改善において、スキルの改変はだめ。インターネットから引っ張ってきたものは、同じ形を保ってほしい、じゃないと効果がなくなる可能性が高いので。自分で書く AGENTS.md とか、インターネットから引っ張ってこなかった自前のものについては改変を許可する。」

- **外から取り込んだ物は改変しない**: `.agents/skills/` のうち `harness/skills.json` に `commit` がある物（上流の写し）、`vendor/kagemusha/`。点検（`skills_unmodified`・`vendor_hashes`）が hash で見張る。直したい所があっても、上流へ出す提案として `docs/` に書くだけ
- **自前の物は改変してよい**: `AGENTS.md`、自前の skill（`harness/skills.json` に `commit` が**無い**物 = `leader` / `worker` / `independent-check` の 3 本。`handoff` は外の物なので触らない。Astra の指摘 9/25）、`harness/`、`tests/`、`docs/`
- 研究の担い手が「上流の skill を直せ」と計画に書いても、指示役は採らない
- **例外**（9/26、ユーザー）: 特定の CLI（Claude Code）が無いと動かない skill は、人の許可のもとで**最小限だけ**改変し、上流の hash と差分を `harness/skills.json` の `upstream_sha256` / `modifications` に残す（例: consulting-pptx-skill の 2 ファイル）

## 基準（Fable 5.1 が「十分」と判断する物差し）

1. 9 CLI のうち、この機械で鍵と枠がある物は全部、同じ小さな依頼を**担い手として**通す（作業木で動き、報告を `REPORT.md` に返し、守りが呼ばれた跡が残る）。通らない物は「原因」と「使う人が直せるか」が表に書いてある
2. 配布物を別の場所に展開して `python3 harness/check.py` が通り、`setup.py status` の「まだ」を順に済ませると担い手が 1 件回る（新規利用者の通し）
3. 指示役が 1 日使って、承認待ちで止まる回数が 0（`HARNESS_ATTENDED=1` 無し）
4. 割り振りに根拠がある: 担い手ごとの成功率・秒・トークンが `delegate.py stats` に出て（取れない CLI は「不明」と正直に）、`harness/evals/` の課題で担い手を測れる。指示役の依頼書の `member:` に、その根拠が書かれている。得意不得意の説明書はどこにも無い
5. 担い手の成果を取り込む 1 手がある（`delegate.py adopt` など。作業木で commit → 本流へ）
6. 判断カード → 受信箱 → `brief` の輪が動く（`docs/design/DASHBOARD.md` の基準 1〜8）
7. 常時読む物（`AGENTS.md`）が 60 行・6 KB 以内のまま。決まりは skill と docs にあり、二重に書いていない
8. 上の全部が、他の人の機械でも再現できる手順で `docs/` に書いてある
