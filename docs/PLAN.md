## MoA の構成（このハーネスの背骨）

> **9/17 夕方に形を変えた。** 初めは役を 7 つ（実装役・調査役・確認役・文書役・相談役・蒸留役）作り、依頼の種類と担い手の得意を突き合わせて自動で選ぶ形だった。ユーザーが示した記事「エージェント開発における悪魔の自転車というアンチパターン」（@voidwarriorchan、2026-09-17）のとおり、**仕事の種類ごとに専用の役を足すと、役・振り分け・引き継ぎの決まりが際限なく増える**。分けてよいのは特別な権限・文脈・知識が要るときだけ。ユーザーの決定:「いいね、進めて」。

### 役は 2 つだけ

| 役 | 誰が | やること |
|---|---|---|
| **指示役** | 人と話す賢いエージェント 1 人（対話で起動した CLI） | 仕事を依頼書に分け、4 つのギアを決めて担い手へ回し、報告と確認の結果を読んで採否を決め、commit する。実作業はしない（小さな直しなどの例外は理由を報告に書く。hook では縛らない） |
| **担い手** | 安くて並べられるエージェント（複数・他社可） | 依頼書 1 枚を実行し、決まった形の報告を返す。読む・探す・書く・実行するは誰でもできる前提で、仕事の種類では分けない |

「調査」「文書」「蒸留」「確認」は役ではなく、**担い手への依頼書の書き方**。役は `harness/delegate.py` が起動した側に `HARNESS_ROLE=worker` を付けて見分ける。印が無ければ指示役。

### ギアは 4 つ（依頼のたびに指示役が決める）

| ギア | 決めること | なぜ分けるか | 依頼書の欄 |
|---|---|---|---|
| **費用** | 誰に頼むか | 賢いモデルは高い。実作業は安い担い手へ。難所だけ高い担い手へ | `member:`（指示役が編成を見て自分で選ぶ。自動の振り分けは作らない） |
| **独立** | 別の人が確かめるか | 同じモデルは同じ所で間違える。確かめる側は、作った物を見る前に「止める形 / 通す形」を書いてから実物を試す。直さない（直しは差し戻す） | `independent_of: <依頼ID>`（その依頼を実行した担い手とは別の会社の担い手を選ぶ。`delegate.py` は同じ担い手を選んだら知らせる） |
| **手の有無** | 触ってよいか、読むだけか | 蒸留や意見出しのように「書けないこと」が安全の境界になる仕事がある。お願いの文ではなく起動の仕方で決める | `hands: none / workspace` |
| **並べる** | 1 人か、何人かに同じ依頼か | 答えが見えない問題は案を並べ、指示役がまとめる（MoA 本来の「提案 × N → 集約」） | `fanout: N`（既定 1） |

新しい種類の仕事が来ても、決めるのはこの 4 つだけ。ギアを足したくなったら、「特別な権限・文脈・知識が要るか」を先に問う。

### 編成（どのモデルを何人用意するかは、使う人が決める）

- 編成ファイル `.loop/team.json`（この機械だけ。配るのはひな形 `harness/team.example.json`）。人が直接書いてもよいし、指示役に「Gemini Flash を 2 人足して」と頼んでもよい。
- 中身は担い手の一覧だけ。1 人 1 行で `name` / `cli` / `model` / `vendor`（会社。独立の判定に使う）/ `cost`（1〜5 の相対値）/ `max_parallel` / `quota_until` / `acp`（起動の仕方）/ `notes`（人が書く覚え書き。得意・不得意など）。
- `delegate.py team` が編成を表で出す。`delegate.py stats` が「どの担い手が何件を何分で、確認に何回で通ったか」を出す。**誰に頼むかを決めるのは指示役**で、道具は材料を出すだけ。
- 担い手の力を見たいときは `harness/evals/` の小さな課題を依頼書として流す（結果は `.loop/evals/`）。

### 流れ（1 件ごと）

```
人 ─依頼→ 指示役 ─依頼書→ 担い手 ─報告→（独立の確認の依頼書 → 別の担い手 ─合否→）指示役 ─採用→ commit
                              ↑────── 差し戻し（最大 2 回）。2 回落ちたら別の担い手か、人へ ──────┘
```

- 依頼書と報告は**ファイル**が正本（`.loop/tasks/<依頼ID>/`）。会話で指示を渡さない。
  - `task.md`: 先頭にギア（`member` / `independent_of` / `hands` / `fanout` / 時間の上限）、本文に 目的 / 受け入れ条件 / 触ってよい場所
  - `report.md`: 何をした / 検証の結果（打った命令と出力の要点）/ 残り / 人の判断が要ること / 変更したファイル。**30 行以内**
  - `events.jsonl`: 起動・終了・合否を 1 行ずつ。指示役はこれを見張って起きる（`sleep` で待たない）
- **担い手は別の作業木（git worktree）で動かす。** 同じ場所を 2 人が書き換えないため。もう 1 つの理由: 上流の訂正の採取（`correction_scan.py`）は会話ログを場所で見分けるので、担い手を同じ場所で起動すると、指示役の依頼文が「人の訂正」として拾われる。
- 費用の決まり: 指示役は差分やログを通読しない（報告・合否・`git diff --stat` を読み、疑わしい所だけ開く）/ 依頼書 1 枚に時間の上限。

## 判断の負荷を減らす（Kagemusha をそのまま使う）

出どころ: https://github.com/yohey-w/kagemusha （MIT）。型と蒸留の道具は `vendor/kagemusha/` に**無編集**で置き、`harness/judgment.py` は機械の仕事だけ包む。
経緯: 初めは「考え方だけ借りて作り直す」で作ったが、上流の設計文書を読まずに要の欄を落としていた。ユーザーの決定:「スキル等を変に自前で構築して効果が落ちるぐらいなら、そのまま使った方がいい。プロンプトインジェクションとかがないか事前にしっかり見ておく必要はある」。検査の記録は `vendor/kagemusha/UPSTREAM.md`。

### 3 つの輪

```
戻せない操作 ─→ ① 判断カード（実行も質問もせず、書いて次の仕事へ）─→ 人がまとめて裁定（1 回に 3 枚まで）
                                                                        │ 裁定・却下は人の言葉のまま
                       ② 台帳（指示役がその場で書く。なぜ(仮説) と 検証 も）←┘
人の訂正（会話ログ）─→ 採取（モデルを使わない。毎日でも無料）
                          │ 5 件たまったら
                          └→ ③ 蒸留（書く手の無い担い手）→ 原則の候補 → **人が確認した物だけ**原則へ
指示役は毎回、薄い原則（32 個・160 行まで）だけ読む → 推奨が人の判断に近づき、🟡 は推奨どおり進められる
```

### 誰が何をするか

| すること | 誰が | 何で |
|---|---|---|
| カード・台帳を書く | 指示役が、上流の型どおりに `.loop/judgment/` のファイルへ直接 | 型の正本は `vendor/kagemusha/templates/`。理由は `docs/decision-cards.md` `docs/judgment-distillation.md` |
| カードの欄の点検 | 機械 | `judgment.py check`（欄の一覧は上流の型から読む。自前の一覧を持たない） |
| 前提ゼロゲート（この 1 枚だけで OK/NG が出せるか） | 文脈を知らない担い手（ギア: 独立 + 手なし） | カードの文面だけを依頼書にする。書いた本人の点検は検収に数えない（上流） |
| 訂正の採取 | 機械 | `judgment.py harvest` → 上流の `correction_scan.py`。子エージェントの発言は上流が除く。**担い手は別の作業木で動かす**ので、依頼文は混ざらない |
| 蒸留 | 書く手の無い担い手 | `judgment.py distill` → 上流の `distill.sh`。全件に行き先が付いた返事だけ受け取る（上流の検査） |
| 原則へ上げる | 人の確認の言葉があったとき、指示役が `judgment_model.md` を直して `judgment.py seal` | 道具の外で書き換わっていたら `brief` が知らせ、中身を出さない |

- 人がいるなら、その場で聞けばよい（カードは要らない）。離れている・長い作業の途中なら、カードにして次へ進む。決めるのは指示役（hook では縛らない）。
- 担い手はカードを書かない。「聞く」操作は guard が止め、担い手は報告の「人の判断が要ること」に書く。
- 判断の中身は repo に入れない（`.loop/judgment/`。`HARNESS_JUDGMENT_HOME` で非公開の別 repo を指せる）。
- 訂正の語彙（`correction_patterns.txt`）は上流が空で配り、このハーネスも中身を配らない。**人に聞き出さず、使いながら覚える**（ユーザーの言葉、9/17:「拾う言葉はユーザーによって異なるから、ハードコートしなくていい。ハーネスが育っていけば、ユーザーの口癖は取得できるので、モデルがそれぞれのユーザーに対して柔軟に判断する感じでいい」）。指示役は、人に直されて台帳へ書くときに、その言い回しが語彙に当たるか確かめ、当たらなければ `judgment.py pattern` で足す。道具は「正規表現として読めるか・何にでも当たらないか・言われた言葉に当たるか」だけ確かめる。
- `cookbook/author/` は読み物。原則へ自動では入れない（借り物は自分の原則と同じ枠を食う、が上流の注意）。
- 今の限界: 上流の蒸留は Claude Code と Codex しか起動できない（`scripts/lib/agent_cli.sh`）。他の担い手に蒸留させる道は P5 のあとで考える。採取が読むのは Claude Code の会話ログ（Codex は上流の `--source codex` で足せる）。

## 設計の軸（最新の知見から）

| # | 軸 | 根拠 |
|---|---|---|
| 1 | **常時読むのは地図だけにする。** `AGENTS.md` は 60 行・6 KB 以内。詳細は skills と `docs/` に置き、必要になったときだけ読ませる | Agent Skills の段階的な読み込み。Codex の project docs は約 32 KiB が上限。旧版は毎回読む量が 23 KB まで膨らんだ |

| 3 | **判定の本体は 1 ファイルだけ。** CLI ごとの違いは設定ファイル 1 枚に閉じ込める（adapter の .py を CLI ごとに作らない） | 旧版では adapter が 7 本あった。DeepSeek Harness は Claude Code と Codex の hook 形式を変換して動かせるので、hook の「話し方」は実質 3 系統（Claude 形式 / Cursor 形式 / JS 拡張）に収まる |

| 5 | **他社の CLI へ仕事を渡すときは、各 CLI の argv を subprocess で起動する。** 自前の配管は作らない | 旧版は自前の配管 3 種（agmsg / Grok stdio / agent_signal）が膨らみの主因だった |
| 6 | **長い作業は、引き継ぎファイルを書いて文脈をリセットする**（会話の要約だけに頼らない） | Anthropic の長時間タスクの手法（compaction だけでは足りない） |
| 7 | **足すなら消す。** 新しい仕組みを足すときは、代わりに消すものを同じ変更で示す | 旧版の 9/16 の反省 |

## 9 CLI の対応表（正本は `harness/clis.json`。実測は 2026-09-17、この機械で）

判定は `harness/guard.py` の 1 本。CLI ごとに持つのは設定 1 枚だけで、CLI ごとの判定の .py は無い（旧版は 7 本あった）。JS で拡張を書く 3 本は共通の橋 `harness/guard_bridge.mjs` を呼ぶ。標準の子エージェントの起動も guard の 1 か所で止める。

実測の形: 無害な命令（`echo`）で hook が呼ばれた記録（`HARNESS_GUARD_TRACE`）を取り、予行の `git clean -fdn`（何も消さないが守りは止める）で「止める」を見た。`.env` や `.pem` を読ませる形は、多くのモデルが `AGENTS.md` の規則に従って**自分から断った**ので hook の実測には使えなかった（規則が効いている証拠ではある）。

| CLI | 版 | 守りの設定 | 話し方 | 実測 |
|---|---|---|---|---|
| Claude Code | 2.1.274 | `.claude/settings.json` | claude | **止めた**（対話の session で `cat .env`。以後、指示役自身が何度も止められている）。`permissions.deny: ["Agent"]` も効いた |

## 守りの決まり（ゼロから作り直す。基準は「戻せるか」。hook の場面は増やさない）

- **deny（止める）**: 各 CLI 標準の子エージェントの起動（止め方が CLI ごとにばらばらなので guard の 1 か所で）/ 壊す命令（作業場の外や木ごとの削除、`git reset --hard`、`git clean -fdx`、ディスク操作など）/ 秘密のファイル（`.env`、鍵、証明書、token、OS の認証情報の置き場）/ 管理者になる操作（`sudo` など。直前にユーザーが OK した 1 回だけ `AGENT_ADMIN_APPROVED=1` で通す）/ main・master への push
- **ask（聞く）**: 外へ出す操作（`git push`、書き込む `gh`、`curl` での送信、遠隔操作）、消す場所が変数で決まらない削除（9/23 に deny から緩和）。**既定では承認画面を出さず止める（人が目の前にいる `HARNESS_ATTENDED=1` のときだけ聞く。人が OK したら `HARNESS_APPROVED=1` を先頭に付けて 1 回だけ通す）。担い手は印があっても常に止める。実行せず、指示役は判断カードへ、担い手は報告へ**（承認の設定が Never の CLI では「聞く」が黙って通りうるため、印で明示する）
- **allow（通す）**: それ以外。外向きでも見るだけの操作は通す。予行（`git clean -fdn`）と、作業場の中の絞り込み付き `find -delete` も通す（9/23 の緩和。「回避されずに守れた数」で守りを測る）
- 判定するのは「実行する命令」と「触る場所」だけで、書き込む中身は見ない
- 限界は `SECURITY.md` に正直に書く（`make` や `bash file.sh` のように、実行する中身が命令の文字列に書かれていないものは止められない）

## 前提（仮定。違えば直す）

1. **起動は原則 YOLO**、配布する設定は YOLO にしない（旧版の 9/13 のユーザー判断を引き継ぐ）
2. **各 CLI 標準の子エージェント（subagent）は止め、他の CLI へ任せる道は `harness/delegate.py` だけにする**（旧版の 9/16 のユーザー判断「ACP 経由だけ」を引き継いだが、実装は 9/19 に ACP をやめ、各 CLI の headless 起動を subprocess で呼ぶ形にした。理由: ACP に対応しない CLI が多く、headless なら 9 本すべてで同じ形にできた）
3. `i-have-adhd`（出力の書き方）と「高校生が一読で分かる言葉」の規則は、ユーザーの好みとして新しく書き直して入れる
4. ~~kagemusha の写し・旧版の承認キュー / 判断の倉庫 / 蒸留便の道具・ponytail は入れない~~ → **9/17 の夕方に取り消し**。自前で作り直した `judgment.py` が上流の要の欄を落としていたため、ユーザーの判断で kagemusha の上流を無編集で `vendor/` に置き、ponytail も skill として取り込んだ（「スキル等を変に自前で構築して効果が落ちるぐらいなら、そのまま使った方がいい」）。旧版の道具（承認キュー / 判断の倉庫 / 蒸留便）は入れない、は変わらない
5. 配布は zip 1 種類（`multiagent-best-template-v3.1.0.zip`）。V2 / V3 の分割はしない
6. python は 3.11 以上（`check.py` が `tomllib` を使う）。守りは標準ライブラリだけで動かす（`delegate.py` も今は標準ライブラリだけ。ACP は使っていない）
7. 役の分担は hook で強制しない（規則で書く）
8. 編成の model 名は配布物に書かない（ひな形は例として書くだけ）。実際の編成は `.loop/team.json` でこの機械だけに置く
9. 役は指示役と担い手の 2 つ。仕事の種類で役を足さない
