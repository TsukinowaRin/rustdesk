ハーネスのブラッシュアップ計画

2026-09-25 ／ 「どういう方向性で、どういう改善をするのか」を全部見える形にした物。誰が何を提案し、指示役（Fable 5.1）が何を採り何を捨てたか、今どこまで進んだかを書く。正本は docs/design/IMPROVE.md と docs/design/DASHBOARD.md。

1. 方向性（何を「良くなった」と呼ぶか）

9/25 に直した。あなたの言葉: 「費用が見えるではなく、効率の良い運用をして、結果として費用を節約できるあるいは効率的にできる、というのが本来の目標。適当なモデルでもできることに Fable 5 を使ったりしないとか、モデルの得意分野を把握して、適切に仕事を割り振るとかが目的。MoA というのはそういうもの。どのモデルが何が得意かはその時によって変わるので、モデルの性質の説明書をハードコードしてはならない。」

ゴールは「入れた人が、文書だけを頼りに、9 本の CLI のどれでも担い手を回せて、止まらず、賢いモデルを要る所だけに使える」ハーネスです。4 つの軸で測ります。

  • 実物で通る — 9 CLI に同じ依頼を流して通るか。文書に書いた命令を新規利用者が打って動くか。
  • 止まらない — 承認待ちで気づかず止まる回数が 0。担い手が終わったら指示役が起きる。
  • 守りは最小限で穴が無い — hook で止めるのは戻せない操作だけ。ただし担い手が守り自身を書き換えられる穴は塞ぐ。
  • 効率よく割り振る — 安いモデルで足りる仕事は安いモデルへ、賢いモデルは要る所だけ。費用の記録（トークン）はそのための手段であって目標ではない。

得意不得意の説明書は持ちません。時期で変わるからです。代わりに 測ります: harness/evals/ の小さな課題を各担い手に流し、成功率・秒・トークンを stats に出す。指示役は依頼書で担い手を選ぶとき、その数字とあなたの指示を根拠にします。測った結果は .loop/ に置き、配布物には入れません（編成のひな形から得意不得意の例文も消しました）。

やらないこと: 外から取り込んだ skill と型の改変（あなたの決まり）/ 新しい CLI の追加 / 見た目のテンプレ化 / 鍵の無い CLI を無理に通すこと。
